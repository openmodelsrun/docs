# Data Flow

This page describes the primary data flows in OpenModels — how data moves from community contributions through validation into the registry, how users discover models via the API, and how telemetry is collected from providers.

## Registry Contribution Flow

When a contributor adds or updates a model, provider, or mapping in the registry, the following sequence occurs:

```mermaid
sequenceDiagram
    participant Contributor
    participant GitHub
    participant Actions as GitHub Actions
    participant Reviewer

    Contributor->>GitHub: Open Pull Request
    GitHub->>Actions: Trigger validate-registry workflow
    Actions->>Actions: Checkout code
    Actions->>Actions: Run validate_registry.py
    alt Validation fails
        Actions->>GitHub: Post failure comment on PR
        GitHub->>Contributor: Request fixes
    else Validation passes
        Actions->>GitHub: Post success comment on PR
    end
    Reviewer->>GitHub: Approve and merge PR
    Note over GitHub: Data available for API ingestion
```

### Validation Steps

The validation pipeline performs the following checks on every pull request:

| Step | Check | Failure Behavior |
|------|-------|-----------------|
| 1 | YAML syntax parsing | Rejects malformed YAML files |
| 2 | JSON Schema validation | Rejects files that don't match schema definitions |
| 3 | Referential integrity | Rejects mappings referencing non-existent models or providers |
| 4 | Duplicate detection | Rejects duplicate model or provider IDs |

## Model Discovery Flow

When a user searches for models or retrieves model details through the API:

```mermaid
sequenceDiagram
    participant User
    participant API as OpenModels API

    User->>API: GET /api/models?search=deepseek-v3
    API-->>User: JSON response with matching models

    User->>API: GET /api/models/deepseek-v3/providers
    API-->>User: JSON response with providers and pricing
```

### API Endpoints

| Endpoint Pattern | Description |
|-----------------|-------------|
| `/api/models` | List and search models with filtering |
| `/api/models/{id}` | Get full model details |
| `/api/models/{id}/providers` | List providers for a model with pricing |
| `/api/models/{id}/compare` | Compare providers side-by-side |
| `/api/models/popular` | Popular models ranked by relevance |
| `/api/providers` | List all providers |
| `/api/search` | Unified search across models and providers |
| `/api/providers/{id}/health`, `/api/providers/{id}/latency` | Provider health and latency data |

## Telemetry Collection Flow

The telemetry system continuously monitors provider health and latency:

```mermaid
sequenceDiagram
    participant Telemetry as Telemetry System
    participant Policy as Probe Policy
    participant Provider as LLM Provider API
    participant API as OpenModels API
    participant User

    loop Hourly at minute 00 UTC
        Telemetry->>Policy: Check if provider enabled
        alt Provider enabled
            Telemetry->>Provider: Send health check request
            alt Provider responds (200/401/403)
                Provider-->>Telemetry: Response received
                Note over Telemetry: Record status: up
            else Provider timeout/error
                Provider-->>Telemetry: Timeout or error
                Note over Telemetry: Record status: down
            end
        end
    end

    loop At 06:15 and 18:15 UTC
        Telemetry->>Policy: Check daily limit
        alt Under limit
            Telemetry->>Provider: Send authenticated inference request (streaming)
            Provider-->>Telemetry: Stream response chunks
            Note over Telemetry: Measure TTFT + total time<br/>Validate semantic response
            Telemetry->>Policy: Increment daily probe count
        end
    end

    User->>API: GET /api/providers/{id}/health
    API-->>User: JSON response with health status

    User->>API: GET /api/models/{id}/providers/ranked
    API-->>User: JSON response with ranked providers
```

### Telemetry Metrics

| Metric | Collection Interval | Retention |
|--------|-------------------|-----------|
| **Health status** | Hourly at minute 00 UTC | 30 days |
| **Time to first token (TTFT)** | At 06:15 and 18:15 UTC | 30 days |
| **Total response time** | At 06:15 and 18:15 UTC | 30 days |
| **Availability (uptime %)** | Computed from health records | Rolling 7 days |
| **Freshness** | Health older than 90 minutes is unknown | Missing metrics are `null` |

### Probe Policies

Each provider can have a custom probe policy controlling:

- **Enabled/disabled** — Whether probes run for this provider
- **Schedule** — Celery beat controls the global cadence above; the policy's `interval_minutes` setting does not reschedule the beat task
- **Daily limit** — Maximum probes per day to control costs (default: 96)

Policies are tracked in Redis with daily counters that auto-expire after 24 hours.

### Provider Ranking Algorithm

When a user requests ranked providers for a model via `GET /api/models/{id}/providers/ranked`, the API computes a composite score:

| Factor | Weight | Source |
|--------|--------|--------|
| Uptime percentage (24-hour rolling) | 40% | Usable health probe records |
| Mean latency (TTFT) | 35% | Provider-wide valid samples in the last 24 hours |
| Mean input/output price per million tokens | 25% | Registry mapping data |

Unknown health/latency earns no credit for that factor but stays `null` in the response. Model provider lists and comparisons use model-specific latency; this ranked endpoint currently uses provider-wide latency. Local TLS trust failures are excluded from uptime rather than counted as provider outages.

## End-to-End Data Lifecycle

The complete lifecycle of data in OpenModels from contribution to user consumption:

```mermaid
sequenceDiagram
    participant Contributor
    participant Registry as GitHub Registry
    participant Pipeline as CI/CD Pipeline
    participant API as OpenModels API
    participant Telemetry as Telemetry System
    participant Providers as LLM Providers
    participant User

    Note over Contributor,User: Phase 1: Data Entry
    Contributor->>Registry: Submit YAML via PR
    Registry->>Pipeline: Validate and merge

    Note over Contributor,User: Phase 2: Enrichment
    Telemetry->>Providers: Probe health and latency
    Telemetry->>API: Feed telemetry metrics

    Note over Contributor,User: Phase 3: Consumption
    User->>API: Query models/providers
    API-->>User: Unified response (model + providers + metrics)
```
